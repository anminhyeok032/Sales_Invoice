# 기존 프로그램(Tradetax.gdb) 데이터 호환 — 계획 및 설계

> 상태: 설계안 (구현 전). 아래 "결정 필요" 항목이 정해지면 단계별로 구현한다.
> 실제 거래처 이름·금액은 이 문서에 넣지 않는다 (`private-data/`는 git에 올리지 않는다).

## 1. 목표

앱에서 만든·고친 거래명세서를 **기존 프로그램이 그대로 열어 쓸 수 있는 `Tradetax.gdb`** 에 반영하고,
기존 프로그램에서 새로 만든 명세서는 다시 앱으로 가져온다. 어느 쪽에서 작업해도 데이터가 어긋나지 않게 한다.

하지 않는 것: 기존 프로그램 자체를 고치거나 대체하는 것, 원본 gdb를 그 자리에서 직접 고치는 것.

## 2. 지금까지 확인된 사실 (원본 gdb 분석)

| 항목 | 내용 |
|---|---|
| 형식 | ODS 10.0, 페이지 4096바이트, 1155페이지, 글자 CP949 |
| 방언 | 리더는 dialect 1로 판정하지만 헤더 플래그 `0x100`은 dialect 3 표시일 가능성 — **엔진으로 확인 필요** |
| 사용자 테이블 | `PUSER`(공급자) 2, `CUSTOMER`(거래처) 134, `TRADFLST`(명세서 헤더) 2,710, `RDESLST`(품목) 23,486, `CUSTMCOST`(단가 기억) 5,381, 빈 테이블 `DUTYFLST`·`ESTFLST` |
| 제약 | 기본키 `CUSTOMER.MCD` 하나. NOT NULL: 모든 테이블의 `HCD`, `CUSTOMER.MCD`. 트리거·제너레이터·프로시저·외래키 없음 |
| 문서번호 `JPNO` | 작성 시각 기반. `YYMMDDHHMMSS`+`P/A` (13자) 1,609건, `YYMMDD`+`A`+5자리 (12자) 1,101건. 중복 없음 |
| 헤더 합계 | `TRADFLST.IMNY/IVAT` = 품목 `IMNY/IVAT` 합 (불일치 0건) |
| 품목 순서 | `ORDRF` 명세서마다 1부터 연속 |
| 품목 금액 | `IMNY ≠ INO×ICOST` 인 줄이 64% — 금액 직접 입력이 정상 |
| 날짜 | 헤더 `IDAY` = `YYYY.MM.DD`. 품목 `MDAY` = `MM.DD` 또는 이어지는 줄 표시(`",.` / `".` / `/.`) 또는 빈칸 |
| 건명 `JKYU` | 대부분 "첫 품목명 … 외 N종]" 형태 (첫 품목명으로 시작 1,833건) |
| 거래처 연결 | 헤더 `MCD` → `CUSTOMER.MCD`. 414건은 `MCD=0`(목록에 없는 직접 입력). 헤더에 상호·대표·사업자번호·주소의 **발행 당시 사본**을 따로 저장(현재 거래처 정보와 다른 것 158건) |
| 기타 고정값 | `HCD`=1(공급자), `CANP`=0, `TAG`='F'(헤더)/'R'(품목)/'C'(거래처), `ETC`='' 대부분 |
| `GCD` | 1(2012~2021), 3(2017~). 최근 것은 3 — 의미 불명, **실험으로 확인 필요** |
| 길이 제한 | 품목명 30바이트, 규격 20, 단위 4, 비고 15, 건명 45, 상호 35, 주소 90 (한글 2바이트) |

앱 쪽 현재 상태:
- 가져오기 JSON(`tradetax-import.json`)은 **손실 변환**이다: `JKYU`, `MCD`, `GCD`, `TAG`, `HCD`, 헤더 사본이 빠진다.
- 앱에서 만든 품목명(금형No 코어 구분)은 가공일지 1,624줄 중 26줄이 30바이트를 넘는다(최대 39).
- 앱 고유 개념: 합친 줄(`mergedFrom`), 필터 상태로 저장한 명세서(`viewKey`), 공급자/공급받는자 명세서별 수정(`*Override`), 계좌번호 등.

## 3. 전체 구조

```
 ┌──────────── 앱 (브라우저, 파일 하나) ────────────┐        ┌──── 동기화 도구 (tools/gdb, 파이썬) ────┐
 │ 저장된 내역(IndexedDB)                             │  ①    │                                          │
 │  + legacy 메타(JPNO·MCD·GCD·사본·동기화 해시)      │──────▶│ sync-out.json 읽기 → 검사 → 변환       │
 │ "기존 프로그램으로 내보내기" → sync-out.json       │        │ → gdb 사본에 쓰기(Firebird 엔진)       │
 │ "기존 프로그램 데이터 가져오기" ← sync-in.json     │◀──────│ → 검증 → 결과 보고 + sync-in.json      │
 └────────────────────────────────────────────────────┘  ②    └──────────────────────────────────────────┘
                                                                         │ ③ 기존 프로그램이 꺼져 있을 때
                                                                         ▼    원본과 교체(백업 보존)
                                                                   Tradetax.gdb
```

브라우저는 gdb 파일을 직접 쓸 수 없고 DB 엔진도 돌릴 수 없으므로, **파일로 주고받는 다리**를 둔다.
앱은 "무엇을 바꿀지"만 JSON으로 내보내고, 실제 gdb 쓰기는 파이썬 도구가 한다.

## 4. 단계별 계획

### 0단계 — 확인 실험 (구현 전, 필수)
기존 프로그램이 있는 PC에서 한다. 아무것도 쓰지 않고 관찰만 한다.

1. 기존 프로그램 버전과 함께 쓰는 DB 클라이언트(`gds32.dll` 등) 버전 확인.
2. **차분 실험**: gdb 사본을 떠 둔 뒤 기존 프로그램으로 ① 명세서 1건 새로 작성, ② 1건 수정, ③ 1건 삭제,
   ④ 거래처 1곳 추가를 각각 하고, 그때마다 리더로 다시 읽어 **바뀐 행을 비교**한다
   (`tools/gdb/diff_tradetax.py` 신규). 이것으로 확정할 것:
   - 새 `JPNO`를 만드는 정확한 규칙, `GCD`·`TAG`·`CANP` 값, `JKYU` 만드는 방식
   - 삭제가 행 삭제인지 표시(`TAG`)인지
   - `CUSTMCOST`(단가 기억)를 언제 갱신하는지
   - 새 거래처의 `MCD` 번호 매기는 방식
3. 테스트용 PC에 Firebird 엔진(ODS 10을 여는 버전: 1.5 또는 2.5, 기존 프로그램과 같은 32/64비트) 준비.
   엔진으로 원본 사본을 열어 **dialect와 무결성 검사(`gfix -v -full`)** 확인.

산출물: 실험 결과 문서, 매핑 규칙 확정.

### 1단계 — 무손실 읽기
- `export_tradetax.py --sync` : 모든 테이블·모든 컬럼을 그대로(원래 이름·타입) 담은 `sync-in.json` 생성.
  행마다 내용 해시(`rowHash`)를 붙인다.
- 앱 가져오기가 이 파일을 읽어, 명세서마다 `legacy` 메타를 보관한다(화면에는 안 보임):
  ```js
  legacy: {
    jpno, hcd, mcd, gcd, canp, tag, etc, jkyu,
    snapshot: { sangho, mname, uptea, upjog, bsno, addr },  // 헤더 사본
    items: [{ ordrf, mday, tag, etc }],                       // 품목별 원래 값
    syncedHash,                                               // 마지막 동기화 때의 내용 해시
  }
  ```
- 거래처에도 `legacyMcd`를 보관해 앱 거래처 ↔ `CUSTOMER.MCD`를 연결한다.
- 기존 `tradetax-import.json` 경로는 그대로 두고, 새 형식이 들어오면 우선 사용한다(하위 호환).

### 2단계 — 앱의 변경 추적
- 명세서마다 `origin`('gdb' | 'app'), `modifiedAt`, 현재 내용 해시를 둔다.
- 상태: `동기화됨`(해시 = syncedHash) / `앱에서 수정됨` / `앱에서 새로 만듦` / `삭제 예정`.
- 저장된 내역 목록에 상태 표시와 필터 추가. 삭제는 바로 지우지 않고 표시만(삭제 정책은 0단계 결과에 따름).

### 3단계 — 내보내기 변환 규칙 (앱 → 기존 형식)
`src/lib/legacyExport.js`(신규, 순수 함수 + 단위 시험).

| 앱 | 기존 | 규칙 |
|---|---|---|
| 명세서 1건 | `TRADFLST` 1행 | 새 것은 `JPNO` = 작성 시각 `YYMMDDHHMMSS`+`P`(0단계 결과로 확정), 충돌 시 1초씩 증가 |
| `date` `YYYY/MM/DD` | `IDAY` | `YYYY.MM.DD` |
| 공급받는자(거래처) | `MCD` + 헤더 사본 | `receiverId` → `legacyMcd`. 목록에 없으면 0. 사본은 실제 인쇄되는 값(명세서별 수정 반영) |
| 새 거래처 | `CUSTOMER` 1행 | `MCD` = 최대값+1 (0단계 규칙 우선) |
| 품목 줄 | `RDESLST` | 합친 줄은 **대표 줄 1개**로. `ORDRF` 1..n 다시 매김 |
| 품목 `date` | `MDAY` | `MM.DD`. 날짜가 빈 이어지는 줄은 기존 표시(0단계에서 확정) |
| 품목명/규격/단위/비고 | `PNAME/PSTAN/PUNIT/ETC` | 바이트 길이 초과 시 **검사 단계에서 막고** 사용자가 고치게 함(자동 자르기는 선택) |
| 수량/단가/공급가액/세액 | `INO/ICOST/IMNY/IVAT` | 그대로(DOUBLE) |
| 헤더 합계 | `IMNY/IVAT` | 품목 합으로 다시 계산 |
| 건명 | `JKYU` | 기존 값 유지, 새 것은 "첫 품목명 외 N종" 규칙(0단계 확정) 45바이트 이내 |
| `HCD/GCD/CANP/TAG` | | 공급자 매핑 / 0단계 확정값 / 0 / 'F','R' |
| 필터로 저장한 명세서 | | 별개 명세서(새 `JPNO`) |
| 계좌번호, 합침 방식, 출력 설정 | 없음 | 내보내지 않음(앱 전용) |

**사전 검사**(내보내기 전에 앱에서 실행, 통과해야 파일 생성):
길이 초과, 금액 합계 불일치, `JPNO` 중복, 날짜 형식, CP949로 못 쓰는 글자(이모지 등), 거래처 미지정.
결과를 표로 보여 주고 해당 명세서로 바로 이동할 수 있게 한다.

산출물: 앱의 "기존 프로그램으로 내보내기" → `sync-out.json`
(바뀐 것만: 추가/수정/삭제 목록 + 각 명세서의 `syncedHash` 기준값).

### 4단계 — gdb 쓰기 도구
`tools/gdb/sync_to_gdb.py`:
```
python tools/gdb/sync_to_gdb.py --db <원본.gdb> --changes sync-out.json --dry-run
python tools/gdb/sync_to_gdb.py --db <원본.gdb> --changes sync-out.json --apply
```
1. 원본을 **사본으로 복사**(원본은 절대 직접 열지 않음). 원본이 열려 있으면(기존 프로그램 실행 중) 중단.
2. 충돌 검사: 앱이 고친 명세서의 gdb 쪽 현재 행 해시 ≠ `syncedHash` 이면 양쪽이 모두 고친 것 → 해당 건 보류, 보고.
3. Firebird 엔진(1단계에서 준비한 버전)으로 사본에 한 트랜잭션으로 INSERT/UPDATE/DELETE.
4. 검증: 엔진 `gfix -v -full` + 우리 리더로 다시 읽어 기대값과 행 단위 비교 + 헤더 합계 불변식 검사.
5. 통과하면 `Tradetax.gdb.bak-YYYYMMDD-HHMMSS`로 원본 보관 후 사본을 원본 자리에 놓는다. 실패하면 아무것도 바꾸지 않는다.
6. 결과 보고서(추가/수정/삭제/보류 건수) + 새 `sync-in.json` 출력 → 앱이 다시 가져와 `syncedHash` 갱신.

엔진 없이 페이지를 직접 쓰는 방식(우리 리더를 쓰기로 확장)은 **채택하지 않는다**:
검증 수단이 우리 리더뿐이라 파일이 깨져도 알기 어렵다. 엔진을 쓸 수 없는 경우에만 별도 검토.

### 5단계 — 반대 방향(기존 프로그램 → 앱) 증분 가져오기
- `sync-in.json`을 가져올 때 `JPNO` 기준으로 새 것/바뀐 것/사라진 것을 나눠 미리보기.
- 앱에서 고친 적 없는(`동기화됨`) 명세서만 자동 갱신, 앱에서 고친 것은 충돌로 표시해 사용자 선택.

### 6단계 — 검증 체계
- **왕복 시험**: 원본 gdb → `sync-in.json` → (변경 없음) `sync-out.json` → 쓰기 → 다시 읽기 = 원본과 행 단위로 같아야 함.
- **골든 시험**: 명세서 1건 추가/수정/삭제, 새 거래처, 합친 줄, 필터 저장 명세서, 길이 초과 등 사례별 기대 결과.
- **실기 시험**: 결과 gdb를 기존 프로그램으로 열어 목록·인쇄·수정이 되는지 사람이 확인(체크리스트).

## 5. 운영 규칙(사용자 안내)
- 동기화는 **기존 프로그램을 끈 상태**에서만 한다.
- 한 명세서를 같은 기간에 양쪽에서 고치지 않는다(고치면 충돌로 보류되어 선택해야 함).
- 동기화 전후로 원본 백업이 자동으로 남는다. 문제 시 백업 파일로 되돌린다.

## 6. 일정 (대략)
| 단계 | 내용 | 규모 |
|---|---|---|
| 0 | 확인 실험, 엔진 준비 | 기존 프로그램 PC에서 반나절 |
| 1 | 무손실 읽기 + 앱 메타 보관 | 1~2일 |
| 2 | 변경 추적 | 1일 |
| 3 | 변환 규칙 + 사전 검사 + 내보내기 | 2일 |
| 4 | gdb 쓰기 도구 + 검증 | 2~3일 |
| 5 | 증분 가져오기 + 충돌 화면 | 1~2일 |
| 6 | 시험 체계 + 실기 시험 | 1~2일 |

## 7. 결정 필요
1. **방향**: 앱 → 기존 프로그램 한 방향만인가, 양쪽 모두 계속 쓰는 양방향인가?
2. **기간**: 기존 프로그램을 언제까지 쓸 것인가(곧 끊을 거면 한 방향·일회성으로 단순화 가능)?
3. **실행 위치**: 기존 프로그램이 있는 PC에 Firebird 엔진과 파이썬을 설치해도 되는가?
4. **길이 초과**: 30바이트 넘는 품목명은 막고 직접 고치게 할지, 자동으로 자를지?
5. **삭제**: 앱에서 지운 명세서를 기존 프로그램에서도 지울지, 남겨 둘지?
